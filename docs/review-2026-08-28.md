## 总体判断

**设计层是这块repo最强的部分。** CONTEXT.md 的词汇表把"确定性模拟""定点空间""战斗整数""Tick 阶段"这些概念的边界和 Avoid 项都钉死了，42 份 ADR 把逐个拍板都留了档。这个密度在同类项目里少见，也是实现能保持整齐的原因。

**确定性的基础设施是干净的**：全仓没有任何 float/double/System.Random/Guid/DateTime（grep 零命中，只有注释和报错文案里出现浮点字样）；所有实体容器都是 `SortedDictionary<long, T>`，遍历天然按 entityId 升序；RNG 按 `(seed, entityId, stream)` 派生且分层；JSON 层明确拒绝浮点输入。这部分做对了。

**但有三处系统性缺口**，按重要性排序：

1. **确定性零回归保护**——第一设计约束，却没有任何"跑两遍比对"的测试。
2. **弹体只有离散点检测，没有扫掠**——已实证高速弹道会穿过敌人。
3. **宿主可控输入能让 `Tick()` 抛异常**——定点数归一化在极短向量上除零。

下面按严重度排列。带 **[实证]** 标记的是我写探针跑出来确认过的。

## 一、严重缺陷

### 1. 弹体隧穿：高速弹道直接穿过目标 **[实证]**

`src/BattleCore/Simulation/BattleInstance.Projectiles.cs:150-193`

`AdvanceProjectiles` 只在**移动前**（:159）和**移动后**（:192）两个离散点做圆-圆检测，中间路径不做扫掠。而地形碰撞反而做了扫掠（`LastSafeProjectilePosition` :210-245）——说明作者意识到了地形需要连续检测，却漏了 Character。

实证结果（同一场景，只改速度）：

| 弹速 | 每帧位移 | 命中窗口（弹 0.2 + 目标 0.5 半径） | 结果 |
|---|---|---|---|
| 6 m/s | 0.2 m | 1.4 m | 命中，HP 100 → 掉血 |
| 60 m/s | 2.0 m | 1.4 m | **穿过，HP 保持 100** |

60 m/s 在 ARPG 里是很普通的箭速/弹速。`ProjectileDefinition.cs:24` 只校验 `speed > 0`，没有任何上限，配置层也不设防。现有测试用的恰好是 `Fix64.FromInt(30)`（1 米/帧，对 1 米直径目标正踩临界），所以这条路径一直没暴露。

**修复建议**：把 `LastSafeProjectilePosition` 的思路推广到 Character——按弹体本帧位移做分段扫掠，或做「线段 vs 圆」的最近距离判定。同时给 `ProjectileDefinition` 加速度上限校验（或明确"每帧位移不得超过弹体半径"的约束）。

### 2. 极短方向向量会让 `Tick()` 抛异常 **[实证]**

`src/BattleCore/Math/FixVector2.cs:9-20` + `Fix64.cs:79-84`

```csharp
public FixVector2 NormalizeOrZero()
{
    if (this == Zero) { return Zero; }              // 只挡住恰好为零
    var length = Fix64.FromRaw(IntegerSquareRoot(
        checked((ulong)LengthSquared.RawValue << Fix64.FractionalBits)));
    return new FixVector2(X / length, Y / length);  // length 可能是 0
}
```

当向量非零但极短时（分量 raw < 256，即长度 < 1/256 米 ≈ 4 mm），`LengthSquared.RawValue` 整除后下溢为 0，于是 `length == 0`，`Fix64.operator /` 的 `ThrowIfZero` 抛 `ArgumentOutOfRangeException`。

**宿主可达路径**：`CharacterState.cs:135` 的 `MovementIntent.Direction(value)` 对外部 `MoveDirectionCommand` 的方向做归一化。实证：传入 `new FixVector2(Fix64.FromRaw(1), Fix64.Zero)` 后 `Tick()` 直接抛异常。同类风险点在 `ResolveAimDirection`（`BattleInstance.Skills.cs:257-279`，目标点极度接近施法者时）。

一个外部输入就能中断整场模拟，这对逻辑核来说是不可接受的失败模式。

**修复建议**：`NormalizeOrZero` 内部改为判断 `length.RawValue == 0` 时返回 `Zero`，而不是只判断原向量是否为零；同时对外部入口的方向做一次健壮性兜底。

### 3. 确定性没有任何回归测试

CONTEXT.md:16 把「相同配置、相同 seed、相同输入 → 任意平台完全一致」列为第一设计约束，并特意写明"第一版不交付帧哈希、命令日志回放等校验工具"不等于"可以破坏确定性"。

但全仓没有任何形式的确定性验证：没有同 seed 跑两遍比对，没有跨实例比对，没有状态哈希。grep 不到任何回放/哈希/一致性测试。

后果是：**任何一次提交都可以静默破坏确定性，而 123 个测试全绿**。（复核注：原文此处以第 5 条为佐证；#5 复核后降级为「依赖未文档化行为、当前无实际不确定性」，但本条缺口本身不受影响——正因为没有回归测试，此类隐患出现与否都无从发现。）

**修复建议**：成本最低且收益最大的是加一个黄金测试——固定 seed 跑 N 帧，把所有事件的 `ToString()` 拼成字符串做快照断言。不需要帧哈希基础设施，也不需要回放工具，几十行就能锁住这条约束。ADR 0015 说"不交付校验工具"指的是不交付给宿主的工具，不应理解为内部也不验证。

## 二、中等缺陷

### 4. 眩晕取消时间轴不彻底，且重复发 `SkillEndedEvent` **[实证]**

`src/BattleCore/Simulation/BattleInstance.Skills.cs:318-355`

```csharp
var cast = caster.ActiveSkill;                 // 局部变量
while (cast.NextEffectIndex < cast.Definition.Effects.Count)
{
    ...
    cast.NextEffectIndex++;
    if (effect.Frame == elapsed)
        ExecuteSkillEffect(...);               // 可能触发眩晕，把 caster.ActiveSkill 置 null
}
if (elapsed < cast.Definition.DurationFrames - 1) { continue; }
caster.ActiveSkill = null;                     // 不校验是否已被取消
events.Add(new SkillEndedEvent(...));          // 无条件再发一次
```

`HandleControlChange`（`BattleInstance.Buffs.cs:328-336`）在眩晕时会清 `ActiveSkill` 并发 `SkillEndedEvent`，但 `AdvanceSkills` 的 while 循环不重新检查，末尾也不校验，于是：

- 同一帧内排在被取消效果之后的效果**照常执行**。实证：技能 frame 0 依次是「给自己上眩晕」和「自伤 25」，眩晕生效后自伤仍然结算（HP 100 → 75）。按契约，时间轴被取消后剩余效果不应再结算。
- 若取消发生在时间轴最后一帧，`SkillEndedEvent` **会发两次**。实证：1 帧时长的自眩晕技能，一帧内产出 2 个 `SkillEndedEvent`。

事件流重复会让宿主的表现层状态机错乱（比如播两次收招动画）。

**修复建议**：while 循环内每次执行效果前检查 `caster.ActiveSkill == cast`，否则 break；末尾改为 `if (caster.ActiveSkill == cast)` 才清空并发事件。

### 5. 多资源消耗遍历 `Dictionary`，依赖未文档化枚举序 **[复核修正：严重度下调]**

`src/BattleCore/Simulation/BattleInstance.Resources.cs:20,29`

```csharp
foreach (var (resourceId, amount) in costs)   // costs 是 Dictionary<string, long>
```

**原结论**（已修正）：称 .NET 字符串哈希按进程随机化会使遍历顺序跨进程/跨平台不稳定，是全仓唯一影响模拟结果的顺序不确定性。

**复核结论**：这个推断不成立。`Dictionary<TKey,TValue>` 在**没有删除操作**时按条目数组（即插入序）枚举，哈希随机化只影响桶分配，不影响枚举顺序。`ResourceCosts` 构建后只读，插入序来自 JSON 解析序，同一配置文件下跨进程/跨平台稳定——**当前不产生不确定性**。

但仍建议修：枚举序是未文档化的实现行为（官方文档明确说顺序 undefined），一旦未来对该字典有删改、或运行时实现变化，就会静默变成真问题。且多资源场景零测试覆盖（所有资源测试只声明单一 `"mana"`）。

**修复建议**（不变）：遍历前按 resourceId 排序（或把 `ResourceCosts` 改成有序结构）。

### 6. 施法者尸体回收时，飞行中的弹体凭空消失 **[实证]**

`src/BattleCore/Simulation/BattleInstance.Projectiles.cs:252-256`

```csharp
if (!_characters.TryGetValue(projectile.SourceId, out var source))
{
    DespawnProjectile(projectile, events);
    return true;
}
```

施法者死亡后尸体还在的窗口期内弹体正常飞行；**尸体被回收（默认 30 帧）的那一刻，弹体立刻消失**。实证：6 m/s 的弹体在施法者死后 40 帧，场上弹体数归零。

这与 ADR 0042 给 AreaEffect 定的规则（"创建者死亡后仍继续"）不一致，也是个能看出来的玩法 bug——射手死后，已经射出去的箭在半空蒸发。

**修复建议**：弹体生成时就快照来源方战斗贡献（AreaEffect 已经这么做了，见 ADR 0042），命中判定不再依赖施法者实体存活。

### 7. 单体技能的 Relation 校验对活体目标失效

`src/BattleCore/Simulation/BattleInstance.Skills.cs:294-303`

```csharp
var matchesRelation = explicitTargets.Any(item => IsRelationMatch(caster, target, item.Relation));
var valid = corpsesOnly
    ? target.IsReviveTarget && matchesRelation
    : target.IsSelectable;      // ← matchesRelation 算了但没用
```

活体分支只看 `IsSelectable`，Relation 被算出来后丢弃。结果是：一个 `Relation = Ally` 的单体治疗技能可以对敌人起手——扣资源、进 CD、发 `SkillStartedEvent`，到生效帧才被过滤成 0 目标。

另外 `explicitTargets` 为空时 `All()` 返回 true，`corpsesOnly` 会错误地变成 true，是个空集合陷阱。

### 8. `MinimumDamage` 语义与契约不符

`src/BattleCore/Simulation/BattleInstance.Combat.cs:166-174`

```csharp
var rawBase = snapshot?.ComputeBase(...) ?? CombatMath.ComputeBase(...);  // 与 :126 重复计算
if (hit == 0 && rawBase > 0) { hit = _config.MinimumDamage; }
```

契约写的是"最终至少 `MinDmg`"，实现是"仅当恰好算成 0 时补到 MinDmg"。默认 `MinimumDamage = 1` 时两者等价，所以一直没暴露；但一旦配成 5，`hit = 3` 不会被抬到 5。顺带一提，`rawBase` 在这里被完整地重算了一遍（:126 刚算过），是纯粹的性能浪费。

## 三、与设计契约的偏离

### 9. `Facing` 不是"1024 档 + 查找表"

契约（CONTEXT.md:28）写的是"角度用整数档（V1 全圆 1024）+ 查找表"。`Math/Facing.cs:23` 实际用的是象限内线性近似 `ay * 256 / (ax + ay)`，在 22.5° 附近误差约 11 档（≈ 3.9°）。功能上够用，但和文档不符，而且没有任何测试锁定档位精度。要么改文档，要么补实现。

### 10. RNG 流：AI 流建了不用，战斗级流缺失

契约（CONTEXT.md:221）要求五类流：战斗级、每 Character 战斗、每 Character AI、每 AreaEffect、每 Buff instance。

实际：只有 Character 战斗流、AreaEffect 流、Buff 流三类在用。`Commands.cs:172` 为每个角色创建了 `AiRng`，但**全仓零消费点**——Brain 完全不用随机；战斗级流也没有。目前这不产生 bug（不消耗就不影响序列），但契约与实现已经脱节，且未来加 AI 随机时容易踩坑（已销毁角色的 RNG 不得被场上效果占用）。

### 11. ~~Buff 周期治疗漏传来源快照~~ **[复核撤回：误报]**

`src/BattleCore/Simulation/BattleInstance.Buffs.cs:265-283`

**原结论**（已撤回）：周期伤害传快照、周期治疗没传，看起来是遗漏；并称 ADR 0036 "没区分伤害和治疗"。

**复核结论**：ADR 0036 明文写了区分——"**Periodic heals stay live (no snapshot) unless later specified.**"；`docs/v1-requirements.md:167` 同文："周期治疗 V1 不快照，来源死亡后停止结算。" 实现（治疗走实时来源、来源死后停止结算）是**按拍板文档执行的设计**，不是 bug。原审查漏读了 ADR 正文最后一句。

仍然成立的部分：`PeriodicHealBuffEffect` 在整个测试套件里零命中，"来源死亡后周期治疗停止"这条已拍板行为没有任何测试锁定（归入 #17）。

### 12. Modifier 结算顺序依赖施加历史

`src/BattleCore/Simulation/BattleInstance.Buffs.cs:189-207`

`RefreshBuffModifiers` 给已有 Buff 叠层时，会先删后加并分配**新的** `modifierId`（:199）。而 `AttributeSet.Get`（`Attributes/AttributeSet.cs:39-42`）是按 instanceId 排序、逐个 `value * (10000 + pct) / 10000` 截断相乘——**逐步截断意味着顺序会影响结果**。

结果是：同一组 Buff，仅仅因为"哪个先叠满层"，算出的属性值可能不同。这仍然满足确定性（相同历史 → 相同结果），但违反了契约"按固定顺序结算"的意图，且迟早会产生难以复现的数值差异报告。

**修复建议**：Percent 类改为先累加再一次性相乘（或改用更高精度的中间表示），让结果与顺序无关。

## 四、性能与架构

### 13. `AttributeSet.Get` 是最热的路径，实现是 LINQ 全表扫描

`src/BattleCore/Attributes/AttributeSet.cs:18-50`

每次 `Get()` 做 1 次 `Where` + `OrderBy` + **3 次独立全表重扫**，每次都分配迭代器与闭包，且没有缓存或脏标记。单次 `ApplyDamage` 就调它 5 次（Combat.cs:132/140/152/159/160），加上移动、技能选敌、暴击判定……在 64 角色规模下这是最集中的一处开销。

同类问题：`CharacterState.HasControl` / `HasUntargetable` / `HasImmuneToDamage`（CharacterState.cs:60-78）每次都全量 LINQ 扫 Buffs × Effects，而 `IsSelectable` 在弹体碰撞和技能选敌里对每个候选目标调用。

**建议**：属性集加脏标记 + 缓存；常用派生量（Controls、护盾总量、是否免伤）在 Buff/护盾变更时增量维护，而不是每次查询重算。

### 14. 地形检测无空间索引

`Movement.cs:175` 和 `Projectiles.cs:247-248` 都是 `_map.Terrain.Any(...)` 线性扫描，且每次调用都分配闭包。弹体扫掠里被调用 `sampleCount + 1` 次，按 V1 上限（256 弹 × 128 地形 × 约 10 次采样）是每帧数十万次判定 + 等量委托分配。当前规模能跑，但没有余量。

### 15. `BattleInstance` 是 15 个 partial 文件组成的 God class

844 行的 Skills、471 行的 Combat、422 行的 Projectiles……全部是 `BattleInstance` 的 partial，共享全部私有字段。这让"某个子系统只能改某几个字段"这种约束完全无法在类型层面表达——比如第 4 条的 bug，本质就是 Skills 循环没有感知到 Buffs 子系统改了 `ActiveSkill`。

不一定现在就要拆，但如果继续加功能，建议至少把阶段之间传递的数据显式化（例如每个阶段接收并返回明确的上下文对象），而不是共享整个实例状态。

## 五、文档与测试的一致性

### 16. `docs/status.md` 措辞易误读 **[复核修正：降级，非自相矛盾]**

**原结论**（已修正）：称第 37 行「已设计、尚未编码：无」与第 43-47 行表格「刷怪表战斗 RNG 随机组成 | 未做」直接冲突。

**复核结论**：两节语义不同——「已设计、尚未编码」与「V1 写了、**未设计完**或未编码」是不同集合，刷怪 RNG 属于后者（需求写了但没设计完），所以「已设计、尚未编码：无」逻辑上自洽，不构成矛盾。但两节标题相似度高、确实容易被接手的人读岔（本报告第一轮就读岔了），建议改措辞或在前一节加一句指向后一节。

### 17. 声称已实现但零测试覆盖的功能

status.md:20 声称 Buff 支持「周期伤/**治**/资源」，但 `PeriodicHealBuffEffect` 在测试中零命中。同类未覆盖：`CombatTriggerKind.Kill`、`TriggerGrantShieldAction`。

另外 `FactionWiped` 被 CONTEXT.md:241、ADR 0039、host-handoff.md:91（列为第一号"会写错的坑"）三处强调，全仓却只有 1 条断言（`CombatPipelineTests.cs:86`）——权重与关注度严重倒挂。

### 18. 测试样板重复

`private static FixVector2 Point(long x, long y)` 在 **16 个文件**里逐字重复；同构的 `BaseAttributes()` / `HeroAttributes()` 在 **8 个文件**重复。这些本应收进已经持有 `Bindings` 的 `TestBattleFactory`（目前只有 65 行、2 个方法）。这本身不是 bug，但它让"加一个边界测试"的成本变高，间接抑制了第 3 条所说的回归测试的添加。
